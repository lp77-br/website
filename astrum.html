Security Assessment — Astrum (app.astrum.mobile)

Security research on an Android app, with responsible disclosure. Updated September 30, 2026.

TL;DR

Security assessment of a GPS-based territory-conquest Android app. I found 11 findings — 2 critical (IDOR in profiles and mass user enumeration), 5 high (excessive GPS track exposure, privilege escalation via PATCH, two GPX-import validation flaws, and undisclosed tracking SDKs), 2 medium (enumeration via signup, exposed Mapbox secret token) and 2 low/informational.

All flaws were reported to the developer before any public disclosure. Some findings were fixed during the process; others were acknowledged and remain pending. No real user data was stored, shared, or used for any purpose beyond the technical confirmation of the vulnerabilities.

1. Context

I found the app by chance (a video by the developer himself on TikTok). Astrum is a GPS-based territory-conquest game — the user runs/walks closing loops that become "territories" on the map, with a public ranking per conquered area.

I started testing through the official interface, without reverse engineering. After finding the first issues, I contacted the developer, who authorized continuing the tests. From there, I deepened the analysis with interception tools and traffic inspection.

The app is under active development by a solo developer, which contextualizes some of the issues found (overloaded functions, absence of legal documentation, etc.). The UI was built with the help of Rork (AI app builder), but all backend logic, database, RPCs, and game mechanics were developed manually. This distinction explains why some protections were correct (storage, rate limit, Pro-plan RLS) while other tables had configuration gaps.

2. Scope and ethical principles

In scope

  • Testing through the app's official interface
  • HTTPS traffic interception via proxy (with authorization)
  • Local storage analysis on a rooted device (own)
  • Direct interaction with APIs (REST + RPCs + Supabase Edge Functions)
  • Extraction of configuration files from the APK (app.config.js, google-services.json)
  • Inspection of metadata and scopes of third-party API keys

Explicitly out of scope

  • Full APK reverse engineering (JADX, apktool)
  • APK modification
  • Access to third-party data beyond the strict minimum needed to confirm findings
  • Destructive tests (DoS, flood, XML bomb)
  • Public disclosure prior to remediation
Critical self-imposed rule: All manipulation tests were performed in remote regions (Amazon and South Atlantic Ocean) with controlled test accounts to avoid impacting real users or polluting the global map.

4. Findings

4.1 — IDOR in profiles: email disclosure of any user

Severity Critical (LGPD — personal data)CVSS 3.16.4 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

The profiles table in Supabase had loose Row Level Security, allowing any authenticated user to read the email of any other user, simply by knowing the UUID.

Reproduction:

curl -s "https://<project>.supabase.co/rest/v1/profiles?select=email&id=eq.<target_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Result: [{"email": "<redacted>"}] — real email of another user.

Impact: Email enumeration + correlation with public name (via ranking) = trivial doxxing. Under LGPD, this constitutes inadequate handling of personal data.

Status: Reported on 09/21. Developer stated some findings were fixed on 09/24, without specific confirmation of this item. Not re-verified.

4.2 — Excessive GPS track exposure via API

Severity High (LGPD — sensitive data, location)CVSS 3.15.9 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

The activities table returns path.coordinates (full GPS track) to any authenticated user, upon knowing the activity ID. Activity visibility between users is an intentional app feature, but the API exposes the full track — not just aggregated data.

Reproduction:

curl -s "https://<project>.supabase.co/rest/v1/activities?select=*&id=eq.<activity_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Impact: Although visibility is intentional, the level of detail exposed allows inferring home and work location, as well as training routine, from the full track. The correct distinction here is not classic IDOR, but excessive data exposure.

Recommendation: Expose only aggregated data (distance, average pace, timestamp) in the public activities API, keeping the full track accessible only to the owner or upon explicit consent.

Status: Reported on 09/21. Developer confirmed that visibility is intentional but acknowledged the need for a scope review. Pending.

4.3 — Mass user enumeration

Severity CriticalCVSS 3.16.4 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

The profiles?select=id,name query, unfiltered, returned the entire user base, with no mandatory pagination or restriction per authenticated user.

Reproduction:

curl -s "https://<project>.supabase.co/rest/v1/profiles?select=id,name&limit=5" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Result: List of real users (names + UUIDs).

Impact: Complete user base is enumerable. Combined with 4.1, it forms a direct pipeline of enumeration → email harvesting.

Status: Reported on 09/21. Developer stated some findings were fixed on 09/24, without specific confirmation of this item. Not re-verified.

4.4 — PATCH on sensitive columns of profiles (privilege escalation)

Severity High (potentially Critical if consumed by RPC/Edge Function)CVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

The profiles table accepted PATCH on sensitive columns via REST API (is_admin, total_points, total_conquests, total_area, territories_owned). The write was accepted (HTTP 200) even though the UI does not render those columns.

Reproduction:

curl -s -X PATCH "https://<project>.supabase.co/rest/v1/profiles?id=eq.<self_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"is_admin": true, "total_points": 999999}'

Result: 200 — columns modified.

Impact: The stats are computed by RPC and the UI does not display them, but the write is accepted in the database. If any RPC/Edge Function consults is_admin for authorization, this is direct privilege escalation.

Status: Reported on 09/21. Developer stated some findings were fixed on 09/24.

4.5 — GPX import accepts future dates

Severity HighCVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

The GPX import feature accepted files with a future timestamp, without server-side validation. I tested with a one-year lead time and the territory was created, with Stars credited.

Why this is more serious than it seems: The app resolves territory conflicts by the most recent activity (if I ran yesterday and you ran today, the territory is yours). A GPX with a future date "reserves" the territory indefinitely — no real run can ever overwrite it. This denies legitimate access to the game.

Status: Reported on 09/14. Developer stated they had previously attempted a fix, but validation was still missing at the time of testing.

4.6 — GPX import accepts open-ocean coordinates

Severity HighCVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

The server does not validate whether the activity occurred on dry land. A GPX centered on an oceanic coordinate (e.g., -23.5000, -42.5000, South Atlantic) was accepted and created a territory.

Impact: Complete absence of geospatial validation on the backend. Allows creation of territories in restricted, military, or inaccessible areas.

Status: Reported on 09/14. Developer questioned the feasibility of full validation but acknowledged the issue. Simple temporal and geospatial validations (bbox, land mask, delta T) are trivial to implement.

4.7 — User enumeration via signup screen

Severity MediumCVSS 3.15.3 AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N

The signup screen returns a distinct message ("This email is already registered") when the email already exists, allowing enumeration of the user base. Precondition for credential stuffing.

4.8 — Mapbox secret token (sk.) exposed in bundle

Severity MediumCVSS 3.15.3 AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N

The APK's app.config.js exposes a Mapbox secret token (sk.eyJ1Ijoi...) in the RNMAPBOX_MAPS_DOWNLOAD_TOKEN field. The token has no administrative scopes, but allows quota and bandwidth abuse (tile download loop on the developer's account).

4.9 — NSAllowsArbitraryLoads: true in iOS infoPlist

Severity Low / hardening

The app.config.js sets NSAllowsArbitraryLoads: true inside ios.infoPlist, globally disabling App Transport Security (ATS) on iOS. Expands the MITM surface on iOS, even with certificate pinning active at higher layers.

4.10 — Undisclosed tracking SDKs

Severity High (LGPD — transparency and purpose)

The app bundle includes analytics/tracking SDKs from multiple vendors (Firebase, Mapbox Telemetry, RevenueCat, and others). The available privacy policy does not detail which SDKs collect data, for what purpose, and under which legal basis. Potential violation of Art. 6 and Art. 9 of the LGPD.

4.11 — Observation: missing maximum-distance validation (not tested)

Severity Informational

I considered importing a GPX with an extremely high distance to check whether the server enforces a limit. I did not execute it because, in the absence of validation (proven in findings 4.5 and 4.6), a track of that magnitude could destabilize older devices or overload the server during geometry processing. I reported it as a technical suspicion without executing it.

5. Good practices observed

  • Supabase storage protected: the activity-imports bucket is correctly isolated per user.
  • Local tampering detection: the app detects modification of the local pro_enabled flag and forces logout. Actual plan validation is server-side.
  • Partial anti-cheat: the system detects obvious anomalies (geographic jumps, impossible paces) and covered a previous incident. It reasonably covers the run flow, but not the GPX import flow.
  • Rate limit on password reset: the 8-digit code has a 1-minute cooldown between attempts, making brute force infeasible.
  • Mapbox: the exposed sk. token is correctly restricted (no administrative scopes).
  • Manual backend: the developer manually implemented the backend logic, RPCs, and critical protections. The RLS failures found are punctual and configuration-related, not architectural.

6. Conclusion

Astrum has a reasonable security baseline in specific areas, but presents configuration flaws in specific tables: misconfigured RLS on tables with personal data, acceptance of PATCH on authorization columns, absence of server-side validation on GPX import, and LGPD compliance gaps.

The most serious findings — email disclosure of any user and mass enumeration of the user base — were reported immediately to the developer, with reproduction scripts and remediation recommendations. The entire process is documented and available for technical discussion.

This report was produced independently, with explicit authorization from the developer. No real user data is included. No information was publicly disclosed prior to remediation.
