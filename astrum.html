Security Assessment — Astrum (app.astrum.mobile)

TL;DR

Análise de segurança de um aplicativo Android de conquista de território baseado em GPS. Encontrei 11 achados — 2 críticos (IDOR em profiles e enumeração em massa de usuários), 5 de severidade alta (exposição excessiva de trajeto GPS, privilege escalation via PATCH, duas falhas de validação na importação de GPX, e ausência de divulgação de SDKs de rastreamento), 2 médios (enumeração via signup, secret token do Mapbox exposto) e 2 de severidade baixa/informativa.

Todas as falhas foram reportadas ao desenvolvedor antes de qualquer divulgação pública. Parte dos achados foi corrigida durante o processo; outros foram reconhecidos e ficaram pendentes. Nenhum dado de usuário real foi armazenado, compartilhado ou utilizado para qualquer fim além da confirmação técnica das vulnerabilidades.

1. Contexto

Encontrei o app por acaso (vídeo do próprio desenvolvedor no TikTok). O Astrum é um jogo de conquista de território baseado em GPS — o usuário corre/caminha fechando circuitos que viram "territórios" no mapa, com ranking público por área conquistada.

Comecei com testes pela interface oficial, sem engenharia reversa. Após encontrar os primeiros achados, entrei em contato com o desenvolvedor, que autorizou a continuidade dos testes. A partir daí, aprofundei a análise com ferramentas de interceptação e inspeção de tráfego.

O app está em desenvolvimento ativo por um desenvolvedor solo, o que contextualiza algumas das falhas encontradas (sobrecarga de funções, ausência de documentação legal, etc.). A interface foi construída com auxílio do Rork (AI app builder), mas toda a lógica de backend, banco de dados, RPCs e mecânicas de jogo foi desenvolvida manualmente. Essa distinção explica por que algumas proteções estavam corretas (storage, rate limit, RLS do plano Pro), enquanto outras tabelas ficaram com lacunas de configuração.

2. Escopo e princípios éticos

Incluído no escopo

  • Testes pela interface oficial do app
  • Interceptação de tráfego HTTPS via proxy (com autorização)
  • Análise de armazenamento local em dispositivo com root (próprio)
  • Interação direta com APIs (REST + RPCs + Edge Functions do Supabase)
  • Extração de arquivos de configuração do APK (app.config.js, google-services.json)
  • Inspeção de metadados e escopos de chaves de API de terceiros

Excluído por decisão própria

  • Engenharia reversa completa do APK (JADX, apktool)
  • Modificação do APK
  • Acesso a dados de terceiros além do estritamente necessário para confirmar achados
  • Testes destrutivos (DoS, flood, XML bomb)
  • Divulgação pública antes de correção
Regra autoimposta crítica: Todos os testes de manipulação foram executados em regiões remotas (Amazônia e Oceano Atlântico Sul) com contas de teste controladas para evitar impacto em usuários reais ou poluição do mapa global.

4. Achados

4.1 — IDOR em profiles: leitura de email de qualquer usuário

SeveridadeCrítica (LGPD — dado pessoal)CVSS 3.16.4 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

A tabela profiles do Supabase estava com Row Level Security frouxo, permitindo que qualquer usuário autenticado lesse o email de qualquer outro usuário, bastando conhecer o UUID.

Reprodução:

curl -s "https://<project>.supabase.co/rest/v1/profiles?select=email&id=eq.<target_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Resultado: [{"email": "<redacted>"}] — email real de outro usuário.

Impacto: Enumeração de emails + correlação com nome público (via ranking) = doxxing trivial. Sob LGPD, configura tratamento inadequado de dado pessoal.

Status: Reportado em 21/09. Desenvolvedor informou ter corrigido parte dos achados em 24/09, sem confirmação específica deste item. Não reverificado.

4.2 — Exposição excessiva de trajeto GPS via API

SeveridadeAlta (LGPD — dado sensível, localização)CVSS 3.15.9 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

A tabela activities retorna o path.coordinates (trajeto GPS completo) para qualquer usuário autenticado, mediante conhecimento do ID da atividade. A visibilidade de atividades entre usuários é uma feature intencional do app, porém a API expõe o trajeto completo — não apenas dados agregados.

Reprodução:

curl -s "https://<project>.supabase.co/rest/v1/activities?select=*&id=eq.<activity_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Impacto: Ainda que a visibilidade seja intencional, o nível de detalhe exposto permite inferir localização de residência, trabalho e rotina de treino a partir do trajeto completo. A distinção correta aqui não é IDOR clássico, mas excessive data exposure.

Recomendação: Expor apenas dados agregados (distância, pace médio, horário) na API pública de atividades, mantendo o trajeto completo acessível somente ao próprio usuário ou mediante consentimento explícito.

Status: Reportado em 21/09. Desenvolvedor confirmou que a visibilidade é intencional, mas reconheceu necessidade de revisão de escopo. Pendente.

4.3 — Enumeração em massa de usuários

SeveridadeCríticaCVSS 3.16.4 AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

A query profiles?select=id,name sem filtro retornava toda a base de usuários, sem paginação obrigatória nem restrição por usuário autenticado.

Reprodução:

curl -s "https://<project>.supabase.co/rest/v1/profiles?select=id,name&limit=5" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>"

Resultado: Lista de usuários reais (nomes + UUIDs).

Impacto: Base completa de usuários enumerável. Combinado com 4.1, forma um pipeline direto de enumeração → coleta de emails.

Status: Reportado em 21/09. Desenvolvedor informou ter corrigido parte dos achados em 24/09, sem confirmação específica deste item. Não reverificado.

4.4 — PATCH em colunas sensíveis de profiles (privilege escalation)

SeveridadeAlta (potencialmente Crítica se consumida por RPC/Edge Function)CVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

A tabela profiles aceitava PATCH em colunas sensíveis via API REST (is_admin, total_points, total_conquests, total_area, territories_owned). A escrita foi aceita (HTTP 200) mesmo sem a UI renderizar essas colunas.

Reprodução:

curl -s -X PATCH "https://<project>.supabase.co/rest/v1/profiles?id=eq.<self_uuid>" \
  -H "apikey: <publishable_key>" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"is_admin": true, "total_points": 999999}'

Resultado: 200 — colunas alteradas.

Impacto: As stats são computadas por RPC e a UI não as exibe, mas a escrita é aceita no banco. Se qualquer RPC/Edge Function consultar is_admin para autorização, é privilege escalation direta.

Status: Reportado em 21/09. Desenvolvedor informou ter corrigido parte dos achados em 24/09.

4.5 — Importação de GPX aceita datas futuras

SeveridadeAltaCVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

A funcionalidade de importação de GPX aceitava arquivos com timestamp no futuro, sem validação server-side. Testei com um ano de antecedência e o território foi criado, com Stars creditados.

Por que é mais grave do que parece: O app resolve conflitos de território pela atividade mais recente (se eu corri ontem e você correu hoje, o território é seu). Um GPX com data futura "reserva" o território indefinidamente — nenhuma corrida real consegue sobrescrevê-lo. Isso nega acesso legítimo ao jogo.

Status: Reportado em 14/09. Desenvolvedor afirmou já ter tentado corrigir anteriormente, mas a validação ainda estava ausente na ocasião do teste.

4.6 — Importação de GPX aceita coordenadas em oceano aberto

SeveridadeAltaCVSS 3.16.5 AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N

O servidor não valida se a atividade ocorreu em terra firme. Um GPX centrado em coordenada oceânica (ex: -23.5000, -42.5000, Atlântico Sul) foi aceito e criou território.

Impacto: Ausência total de validação geoespacial no backend. Permite criação de territórios em áreas restritas, militares ou inacessíveis.

Status: Reportado em 14/09. Desenvolvedor questionou a viabilidade de validação completa, mas reconheceu o problema. Validações temporais e geoespaciais simples (bbox, land mask, delta T) são triviais de implementar.

4.7 — Enumeração de usuários via tela de cadastro

SeveridadeMédiaCVSS 3.15.3 AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N

A tela de cadastro retorna mensagem distinta ("Esse e-mail já está registrado") quando o email já existe, permitindo enumeração da base de usuários. Pré-condição para credential stuffing.

4.8 — Secret token do Mapbox (sk.) exposto no bundle

SeveridadeMédiaCVSS 3.15.3 AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N

O arquivo app.config.js do APK expõe um secret token do Mapbox (sk.eyJ1Ijoi...) no campo RNMAPBOX_MAPS_DOWNLOAD_TOKEN. O token não possui escopos administrativos, mas permite abuso de quota e banda (download de tiles em loop na conta do desenvolvedor).

4.9 — NSAllowsArbitraryLoads: true no infoPlist do iOS

SeveridadeBaixa / hardening

O app.config.js define NSAllowsArbitraryLoads: true dentro de ios.infoPlist, desabilitando globalmente o App Transport Security (ATS) no iOS. Amplia superfície de MITM em iOS, mesmo com certificate pinning ativo em camadas superiores.

4.10 — Ausência de divulgação de SDKs de rastreamento

SeveridadeAlta (LGPD — transparência e finalidade)

O bundle do app inclui SDKs de analytics/rastreamento de múltiplos fornecedores (Firebase, Mapbox Telemetry, RevenueCat e outros). A política de privacidade disponível não detalha quais SDKs coletam dados, com qual finalidade e sob qual base legal. Potencial violação dos Art. 6º e Art. 9º da LGPD.

4.11 — Observação: ausência de validação de distância máxima (não testado)

SeveridadeInformativa

Considerei importar um GPX com distância extremamente alta para verificar se o servidor impõe limite. Não executei porque, na ausência de validação (comprovada nos achados 4.5 e 4.6), um trajeto dessa magnitude poderia instabilizar dispositivos antigos ou sobrecarregar o servidor durante o processamento de geometria. Reportei como suspeita técnica sem executar.

5. Boa prática observada

  • Storage do Supabase protegido: o bucket activity-imports está corretamente isolado por usuário.
  • Detecção de manipulação local: o app detecta alteração do flag local pro_enabled e força logout. A validação real do plano é server-side.
  • Anti-cheat parcial: o sistema detecta anomalias óbvias (saltos geográficos, paces impossíveis) e cobriu um incidente anterior. Cobre razoavelmente o fluxo de corrida, mas não o fluxo de importação GPX.
  • Rate limit em reset de senha: o código de 8 dígitos tem cooldown de 1 minuto entre tentativas, inviabilizando brute force.
  • Mapbox: o sk. exposto está corretamente restrito (sem escopos administrativos).
  • Backend manual: o desenvolvedor implementou manualmente a lógica de backend, RPCs e proteções críticas. As falhas de RLS encontradas são pontuais e de configuração, não de arquitetura.

6. Conclusão

O Astrum tem uma base de segurança razoável em pontos específicos, mas apresenta falhas de configuração em tabelas específicas: RLS mal configurado em tabelas com dados pessoais, aceitação de PATCH em colunas de autorização, ausência de validação server-side na importação de GPX, e lacunas de compliance sob LGPD.

Os achados mais graves — leitura de email de qualquer usuário e enumeração em massa da base — foram reportados imediatamente ao desenvolvedor, com scripts de reprodução e recomendações de correção. O processo completo está documentado e disponível para discussão técnica.

Este relatório foi elaborado de forma independente, com autorização explícita do desenvolvedor. Nenhum dado de usuário real está incluído. Nenhuma informação foi divulgada publicamente antes da correção.
