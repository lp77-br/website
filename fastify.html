Fastify 5.12.8 — Schema content-type bypass

Independently discovered. Closed by maintainers as not a vulnerability; a public hardening fix is tracked.

Status: Closed (Not a Vulnerability). Maintainer @mcollina confirmed the technical accuracy but classified the behavior as expected per the framework's threat model. A correctness/hardening fix (PR #6969) is being tracked publicly.

Summary

When a route's schema.body.content or schema.response[code].content key includes media type parameters (e.g., application/json; charset=utf-8), Fastify accepts and compiles the schema but never applies it. Request body validation and response serialization are silently skipped.

Technical details

Fastify stores content keys exactly as written during schema compilation, but at request time, it looks up the parsed media type only (parameters stripped). Thus, the keys never match.

The maintainers noted that this has been reported and closed several times before (e.g., GHSA-26rh-p642-7f35, GHSA-j2xv-r62g-hmmh). The trigger is the developer's schema configuration, which their threat model treats as trusted. In v6 (main), response fallback is removed, failing closed with FST_ERR_MISSING_CONTENTTYPE_SERIALIZATION_FN. For v5, the workaround is to use the bare essence media type (e.g., application/json).

Impact & Resolution

Applications relying on the schema as their only validation boundary may receive unexpected input, and fields outside the schema may be returned to clients. While closed as not a vulnerability (since it requires developer misconfiguration), the lack of a startup warning was acknowledged as a 'footgun'. The maintainers are adding this case to the non-vulnerabilities list in SECURITY.md.

This finding was discovered independently and reported responsibly. No data was compromised. The maintainers' classification is respected.
